## 第 1 章 问题定义与设计红线

### 1.1 这个系统不是什么

**它不是「AI 批作业」。** 凡是把自己定位成"自动给学生打分"的评阅系统，都会撞上同一堵墙：一旦出错，产品就从"效率工具"变成了"责任主体"，而责任无法外包给模型。

**它是「把教师脑中的评分标准显性化，并把其中可机械化的部分从人身上挪走」。**

### 1.2 执行问题与判断问题

这是全系统的底层分类，后面所有设计都从它推导出来。

| 类型 | 特征 | 处理方式 |
|---|---|---|
| **执行问题** | 有确定答案，可被核验 | 可以完全交给机器 |
| **判断问题** | 没有确定答案，需要有人承担后果 | **必须留给人** |

具体到评分工作：

| 可交给机器（执行问题） | 必须留给人（判断问题） |
|---|---|
| 读取与解析文档、代码 | 制定与修改评分标准 |
| 运行代码并核对结果 | 定性判断：创新性、表达质量 |
| 定位评分点对应的原文证据 | 有后果的判定：雷同定性、及格线 |
| 计算相似度信号 | 判断学生真实的理解程度 |
| 聚合班级统计与共性 | 最终确认与签字 |
| 生成评语草稿 | 判断教学如何调整 |

### 1.3 三条设计红线

> 违反其中任何一条，本系统的输出都不可信，且不可申诉。

#### 红线一：观察层不得含任何定性判断

判据是一个可操作的问题：

> **「没找到」是事实，「不合格」是判断。**

| ✅ 观察 | ❌ 判断 |
|---|---|
| 在 §2.1 找到原文：「……」 | 原理说明写得完整 |
| 在 p.3-4 内检索 waitpid，未找到匹配 | 缺少对 waitpid 的处理 |
| 正文 p.2 称使用多进程；代码 p.6 仅 1 次 fork，无 wait 调用 | 正文与代码矛盾，涉嫌造假 |
| 评分点要求的 r2 未获得匹配 | 该评分点不合格 |

**实现方式**：三层防线（Prompt 禁用词表 → Zod 枚举约束 → 程序后置扫描）。详见第 5 章。

#### 红线二：分数由程序确定性计算

`总分 = 100 × Σ(权重 × 档位系数) / Σ权重`，纯函数，无模型参与。

**为什么不能让模型出总分**：一次生成的总分不可复现、不可追溯。教师无法解释"这 76.5 分怎么来的"，学生申诉时无从复核。确定性算分让每一分都可定位到具体评分点与具体档位。

#### 红线三：有后果的判定永不自动化

| 判定 | 为什么不能自动化 |
|---|---|
| 抄袭 / 雷同定性 | 相似度高不等于抄袭。同模板、同教材范例、教师发的 starter code、同宿舍讨论都会产生高相似度。定性需要解释规则，而规则是人定的 |
| 及格线附近 | 后果不对称。差 1 分及格与差 1 分不及格，对学生的意义完全不同，必须有人签字 |
| 创新性、表达质量 | 没有可判定的依据。给它打分，本质是生成一个稳定的伪随机数——它会一致，但不会正确 |

**实现方式**：在数据契约层面就禁止。`5_surface_conflicts.nature` 的枚举为闭集，不含任何诚信类词汇；总分跨及格线时程序强制挂起。

## 第 2 章 主链路与数据流

### 2.1 五段式主链路

```
①  评分细则 + 少量手改样本
        ↓
②  结构化证据提取（观察层，7 字段，零定性）
        ↓
③  带证据引用的自然语言评价
        ↓
④  等级匹配（L1–L4）
        ↓
⑤  程序确定性计算分数
        ↓
⑥  教师确认与校准
```

### 2.2 每段的输入输出契约

| 段 | 输入 | 输出 | 由谁执行 | 关键约束 |
|---|---|---|---|---|
| ① | 教师手工书写的评分细则；可选的历史批改样本 | `Rubric` JSON | 人 + 程序辅助 | `judgment` 类型评分点不进入自动流程 |
| ② | `Rubric` + 解析后的报告文本 | `EvidenceExtraction` JSON | 模型 + 程序后处理 | **零定性**；引文必须回查通过 |
| ③ | `EvidenceExtraction` | 带 `quote_id` 引用的自然语言段落 | 模型 | 每句话必须能指向证据；不得引入新事实 |
| ④ | `EvidenceExtraction` + `levels` | `LevelMatch` JSON | 模型 + 程序前置规则 | 只出档位不出分；证据不足转人工 |
| ⑤ | 全部 `LevelMatch` + 权重 | `FinalGrade` JSON | **纯程序** | 确定性；可复现 |
| ⑥ | `FinalGrade` | 确认后的成绩 + `calibration_signals` | 人 | 改档必填 `reason_code` |

### 2.3 端到端数据流

```
上传报告 ──► R2（原始文件）
              │
              ▼
       解析（unpdf / mammoth / 降级 toMarkdown）
              │
              ▼
        R2（解析后 markdown + 锚点索引）
              │
              ├──► 阶段 A：全篇章节索引 ──► D1
              │
              ▼
       阶段 B：按评分点分组抽取（并发 5）──► 引文回查 ──► D1
              │
              ▼
        程序计算 6_sufficiency
              │
              ▼
         等级匹配（逐评分点）──► D1
              │
              ▼
        程序确定性算分 ──► D1
              │
              ▼
       教师确认 / 改档 ──► calibration_signals ──► D1
```

**每一步的中间产物都落库**，理由有两个：崩溃可续跑；任何一分都能回溯到它的证据来源。

## 第 3 章 技术架构

### 3.1 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 运行时 | Cloudflare Workers（**Free 起步**，撞限再升 Paid） | 公网可访问。官方文档明示 `fetch()` 等待不计入 CPU 时间，所以长耗时 LLM 调用不撞限制。**唯一吃 CPU 的大户是本地 PDF 解析，把它外移即可留在 Free** |
| 批量编排 | Cloudflare Workflows | `step.do()` 单步 wall time 无上限、失败独立重试、`waitForEvent()` 可挂起等教师确认 |
| 路由框架 | Hono | 轻量、无 Node 依赖、Workers 生态首选 |
| 模型 | DeepSeek `deepseek-flash` | 中文与代码混合输入表现好；JSON Output 模式；约 ¥0.1/份 |
| 校验 | Zod | 契约先行，输入输出双向校验 |
| 解析 | **主路径：`env.AI.toMarkdown()`**；备选：`unpdf`（PDF）+ `mammoth`（DOCX） | `toMarkdown` 是服务调用，不占本地 CPU，是 Free 版可行的关键。`unpdf` 仅在升级 Paid 后可作本地兜底。**不可用 `pdfjs-dist`**（依赖 DOM/Canvas） |
| 存储 | R2 + D1 | Workers 无持久文件系统，产物必须落对象存储 |
| 前端 | Vite + React SPA | 构建产物作为 Workers Static Assets |
| 测试 | Vitest | 算分引擎与校验逻辑必须覆盖 |

### 3.1.1 版本策略：先 Free，撞限再升 Paid

**结论修正记录**：本文早期版本要求「必须升级 Workers Paid（$5/月）」，该结论建立在「PDF 解析在 Worker 本地用 `unpdf` 跑」这一前提上。**把解析外移后，Free 版够用。**

Free 版 `10ms CPU / 请求` 只计算 CPU 实际执行时间，**不计网络等待**：

| 操作 | 占 CPU | 说明 |
|---|---|---|
| 调 DeepSeek 等 20 秒 | ❌ 不占 | `fetch()` 等待期间不消耗 CPU |
| `env.AI.toMarkdown()` 解析 PDF | ❌ 不占 | 平台服务调用，非本地计算 |
| Hono 路由 + JSON 解析 + Zod 校验 | ✅ 占，约 2–5ms | 在预算内 |
| 引文回查（原生 `indexOf`） | ✅ 占，约 1ms | 在预算内 |
| **`unpdf` 本地抽取 10 页 PDF 文本** | ✅ **占，几十到几百 ms** | **超预算，必须外移** |

因此本方案的默认路径是：

| 顺序 | 做法 | 成本 |
|---|---|---|
| 1 | **PDF / DOCX 文本抽取一律走 `env.AI.toMarkdown()`** | 0（消耗 Workers AI 免费额度） |
| 2 | 浏览器端做即时预览解析，Worker 只处理纯文本 | 0 |
| 3 | 大 JSON 用轻量手写校验替代重量级 schema | 0 |
| 4 | 上述仍撞限 → 升级 Workers Paid（$5/月） | $5/月 |

**为什么把 Paid 放最后**：开通 Paid 需要绑定 Visa / Mastercard 双币信用卡，国内银联卡多数不支持，这是实际障碍。**先用 0 成本路径验证，撞限信号真出现再处理。**

具体操作步骤见 [环境搭建指南](环境搭建指南.md)。

### 3.3 分层职责

| 层 | 做什么 | 明确不做 |
|---|---|---|
| `routes/` | 解析请求、校验入参、调用服务、格式化响应 | **不写业务逻辑** |
| `services/` | 承载业务规则与编排；多步写入走事务 | **不依赖请求/响应对象**，可独立单测 |
| `repo/` | 数据查询与外部调用 | 不含业务判断；避免 N+1（批量查询而非循环查） |
| `llm/` | 模型调用、JSON 守卫、重试 | 不含业务规则 |

`scoringService` 是纯函数：输入 `LevelMatch[]` + 权重，输出 `FinalGrade`。它必须 100% 单测覆盖，因为分数是这系统里唯一不能出错的部分。

### 3.4 存储选型

| 存储 | 存什么 | 不存什么 |
|---|---|---|
| **R2** | 原始上传文件、解析后 markdown、锚点索引、评测快照 | 结构化查询字段 |
| **D1** | `rubric` / `submission` / `evidence` / `levelmatch` / `grade` / `calibration_signal` | 大文本（放 R2） |
| **KV** | 仅缓存 rubric 版本号、prompt 版本指纹 | **评分记录**（Free 写额度仅 1000/天） |

容量估算：30 份报告 × 20 个评分点 × 约 2KB 证据 ≈ 1.2 MB，D1 Free 的 500MB 绰绰有余。

```bash

```

- Key 只存在于 Worker 侧，读 `env.DEEPSEEK_API_KEY`

### 3.6 批量执行模型

**这是最容易踩的坑。**

```
POST /api/grade/batch
  → 写入 D1 任务记录
  → env.GRADE_WORKFLOW.create({ params: { taskId } })
  → 立即返回 202 + taskId

Workflow:
  for each submission:
    step.do(`parse:${id}`, ...)      # 独立重试
    step.do(`evidence:${id}`, ...)
    step.do(`levelmatch:${id}`, ...)
    step.do(`score:${id}`, ...)
  step.waitForEvent('teacher-confirm')   # 可挂起等待人工
```

**禁止在单个 HTTP 请求内串行处理多份报告。** 客户端一断连，所有关联任务立即取消；`ctx.waitUntil()` 也只额外保活 30 秒。

前端通过**轮询任务状态**获取进度，不用长连接等待。

## 第 4 章 数据契约

四份核心契约：`Rubric`、`EvidenceExtraction`、`LevelMatch`、`FinalGrade`。

**完整 JSON Schema 与字段说明见 [附录 A](附录-数据契约与Prompt.md#a-数据契约)。** 本章只列实现时必须记住的三条硬性约束。

### 4.1 约束一：观察层去定性化

三层防线，缺一不可：

| 层 | 机制 | 失败处理 |
|---|---|---|
| L1 Prompt | 禁用词表 + 句式模板 + 自检指令 | 无效则进入 L2 |
| L2 Schema | Zod 枚举约束，`nature` 等字段为闭集 | 校验失败即拒收 |
| L3 后置扫描 | 程序扫描输出中的禁用词 | **命中即拒收并重生成，最多 2 次，仍失败置 `needs_human`** |

只有 L3 把"防定性"从口头承诺变成机器约束。

### 4.2 约束二：`6_sufficiency` 由程序判定

不让模型自由判断"材料是否足够"。程序按 `evidence_requirements` 逐条比对 `section` / `code_symbol` / `figure`，产出 `req_results`。

这样 `insufficient` 就是一个可核验的事实陈述（"r2 未满足"），而不是"这份报告不够好"。

### 4.3 约束三：位置以程序计算为准

模型给出的 `char_start` / `char_end` **一律不信任**。程序在解析文本中对 `found_quotes[].text` 做匹配：

| 匹配结果 | 处理 |
|---|---|
| 精确子串命中 | 回填真实偏移，`verified = "exact"` |
| 归一化相似度 ≥ 阈值（默认 0.9） | 回填偏移，`verified = "fuzzy"` |
| 未命中 | **丢弃该 quote**，记录 `QUOTE_NOT_VERIFIABLE` |

**这是整套系统防幻觉的核心机制**，也是评测里最重要的信任基石。

## 第 5 章 LLM 工程设计

### 5.1 接口选型

| 项 | 选择 | 理由 |
|---|---|---|
| 模型 | `deepseek-flash` | 长上下文、中文与代码混合表现好 |
| 结构化输出 | **JSON Output 模式**（`response_format: {"type":"json_object"}`） | 本任务只需"填满一个固定结构"，不需要模型在生成过程中调用外部函数。JSON mode + Zod 是最简单可靠的组合 |
| `temperature` | `0` | 评分需要可复现 |

> 实施前请在 DeepSeek 控制台确认当前模型 ID 与价格，本文口径为 2026-08 文档。

### 5.2 JSON Output 的已知坑与应对

官方文档明确列出以下注意事项，必须逐条应对：

| 坑 | 应对 |
|---|---|
| 必须在 prompt 中**出现 "json" 字样**并提供示例 | 所有 prompt 均已包含字段示例 |
| 必须设置合理的 `max_tokens`，否则 JSON 被截断 | 按输出规模设置：索引 1500，抽取 4000，匹配 1500 |
| **偶发返回空 `content`** | 视为可重试失败；连续 2 次则置 `needs_human`，**不静默填充** |

### 5.3 两阶段切块

| 阶段 | 目的 | 调用次数 |
|---|---|---|
| A：全篇章节索引 | 建立全局地图，让「未找到」有全局依据 | 1 次 / 报告 |
| B：按评分点分组抽取 | 每 4–6 条一组，注入全篇索引 + 相关切片 | ⌈N/5⌉ 次 / 报告 |

**为什么必须两阶段**：抽取是分块进行的。没有全篇索引，「未找到」就只能基于局部切片判断，会把"在别处但没看到"误报成"不存在"。

### 5.4 并发与重试

| 项 | 策略 |
|---|---|
| 并发 | 阶段 B 的 5 组用 `Promise.all` 并行；**并发数上限 5**（Workers 并发出站连接限制为 6，要留余量） |
| 重试 | 指数退避 3 次：0.5s / 2s / 8s |
| 重试范围 | 仅 HTTP 429 与 5xx |
| 不重试 | 其余 4xx，直接失败并记录 |

### 5.5 非法 JSON 降级链

```
1. JSON.parse 直接解析
2. 抽取 ```json 围栏内内容
3. 机械修复：去 BOM、去尾逗号、补右括号
4. 重试 1 次（temperature=0，追加"只输出 JSON，不要解释"）
5. 二次失败 → 该评分点标记 needs_human，写入 7_parse_failures
```

**原则：宁可标记为"需要人工"，也不静默填充一个猜测值。**

### 5.6 引文回查（quoteVerify）

这是把"防幻觉"落成机器约束的关键，实现在 `util/quoteVerify.ts`：

```ts
function verifyQuotes(evidence, parsedTexts) {
  return evidence["2_found_quotes"].flatMap(q => {
    const text = parsedTexts.get(q.material_id);
    const exact = text.indexOf(q.text);
    if (exact >= 0) {
      return [{ ...q, location: { ...q.location, char_start: exact, char_end: exact + q.text.length },
                verified: "exact" }];
    }
    const fuzzy = fuzzyFind(text, q.text);           // 归一化后相似度
    if (fuzzy.similarity >= MIN_SIMILARITY) {
      return [{ ...q, location: { ...q.location, char_start: fuzzy.start, char_end: fuzzy.end },
                verified: "fuzzy" }];
    }
    return [];                                        // 丢弃，并记录 QUOTE_NOT_VERIFIABLE
  });
}
```

**注意**：`char_start` / `char_end` 一律以程序计算结果为准，覆盖模型给的值。

## 第 6 章 等级匹配与确定性算分

### 6.1 档位体系

每条评分点分 4 档，系数可在 rubric 中按点自定义：

| 档位 | 系数 | 含义 |
|---|---|---|
| `L4` | 1.0 | 完整覆盖全部要点 |
| `L3` | 0.8 | 覆盖主要要点，个别次要要点缺失 |
| `L2` | 0.5 | 覆盖部分要点，存在明显缺失 |
| `L1` | 0.2 | 近乎未涉及 |

### 6.2 算分公式

```ts
// services/scoringService.ts —— 纯函数，无 IO，无模型
raw_score_i    = weight_i × score_ratio(level_i)
computed_total = 100 × Σ raw_score_i / Σ weight_i     // 权重和不必为 100
final_total    = round_half_up(computed_total, 1) + Σ override_delta
```

`needs_human = true` 的评分点**不参与求和**，其权重也不计入分母。

### 6.3 封顶与挂起规则

| 规则 | 触发条件 | 效果 |
|---|---|---|
| `cap_level_when_required_missing` | `required` 证据未满足 | 该点评分**上限**为指定档位（默认 L2） |
| `unresolved_conflict` | 存在未解决的 `factual_mismatch` | **不自动定级**，`needs_human = true` |
| `parse_failure` | 材料解析失败 | **不自动定级**，`needs_human = true` |
| `criterion_is_judgment` | 评分点 `type = judgment` | 直接转人工 |
| 及格线 | 总分跨 `pass_line` | 强制 `state = pending_teacher_confirm`，**程序不输出及格结论** |

前四条由**程序在调用模型之前**判定，模型只在剩余需要判断的部分工作。这样能最大程度压缩模型犯错的空间。

### 6.4 为什么不让模型出总分

| 问题 | 模型出总分 | 程序算总分 |
|---|---|---|
| 可复现 | ✗ 同输入可能不同输出 | ✓ |
| 可追溯 | ✗ 说不出 76.5 从哪来 | ✓ 每一分可定位到评分点与档位 |
| 可校准 | ✗ 改规则要重训 | ✓ 改权重即可 |
| 可申诉 | ✗ 无法解释 | ✓ 可出示证据链 |

## 第 7 章 教师确认与校准

### 7.1 UI 三层下钻

教师必须能回答"这一分是怎么来的"。设计为三层：

| 层 | 内容 |
|---|---|
| **L1 总分条** | 每条评分点的 `weight × ratio` 堆叠构成，满分区 vs 实得区用不同色阶区分 |
| **L2 评分点** | 点开某点 → 档位、系数、支撑引文列表、未满足的 `req_id`、冲突提示、被阻断的更高档位及原因 |
| **L3 原文定位** | 点引文 → 跳转原文对应位置并高亮（R2 markdown + anchor 定位） |

L3 是申诉场景下的关键：教师能直接出示"扣分依据在第 3 页第 2 段"。

### 7.2 改档必填原因

改档时**必须**从枚举中选择 `reason_code`，可选备注：

| `reason_code` | 含义 |
|---|---|
| `rule_too_strict` | 细则过严 |
| `rule_too_loose` | 细则过松 |
| `evidence_misread` | 证据被误读 |
| `material_missing` | 材料缺失导致误判 |
| `other` | 其他（`teacher_note` 必填） |

**为什么强制枚举**：自由文本无法统计。枚举化的原因码才能回答"系统在哪一类评分点上系统性偏严"，这是规则迭代的输入。

### 7.3 校准信号只建议、不自动改规则

教师的每次改档都记为 `calibration_signals`。这些信号用于：

1. **生成规则修改建议**：某条评分点连续 5 次被 `rule_too_strict` 改档 → 提示复核该条的档位描述
2. **不自动改规则**。规则变更必须由人确认，写入新的 `rubric.version`，并**触发一次评测回放**验证是否引入回归

### 7.4 状态机

```
draft → evidence_extracted → level_matched → scored
                                                ↓
                                      pending_teacher_confirm
                                                ↓
                                      teacher_confirmed → archived
```

`pending_teacher_confirm` 是强制关卡，不允许跳过直接归档。

| 页面 | 关键交互 |

1. 教师填写 ≤15 条评分点（每条含名称、权重、档位描述）

## 第 9 章 评测方案

### 9.1 原则：按评分点比对，不按总分

总分相近会掩盖大量逐点错误。两个系统都给出 76 分，可能一个在 20 个点里错了 8 个、另一个只错了 1 个。

### 9.2 指标与阈值

| 指标 | 计算方式 | 阈值 |
|---|---|---|
| **引文可定位率** | 人工抽查 `found_quotes` 能在原文命中的比例 | **≥ 0.95（硬门槛）** |
| **定性词越界率** | 观察层出现禁用词的条数 | **= 0（硬门槛）** |
| **二次加权 Kappa（QWK）** | 等级为有序变量，用 quadratic weights | ≥ 0.6 可接受 / ≥ 0.8 良好 |
| 逐点档位一致率 | 完全一致的对数 / 总对数 | ≥ 65% |
| 总分 MAE | \|AI 总分 − 教师总分\| 均值 | ≤ 5 |
| 缺失项召回 | 教师判缺失且系统也 `not_found` 的比例 | ≥ 0.8 |
| 过度自信率 | 系统自动定级但教师改档的比例 | ≤ 20% |

**为什么用 QWK 而非普通 Kappa**：`L1–L4` 是有序等级，普通 Kappa 把「L1 vs L4」和「L1 vs L2」视为同等不一致，会严重低估一致性。QWK 对方差大的错配施加二次惩罚，更贴合评分场景。

### 9.3 样本量与流程

| 项 | 要求 |
|---|---|
| 最小样本 | **n = 20 份 × 20 点 = 400 个判定对** |
| n < 15 | 只能看趋势，不能下结论 |
| 盲评要求 | **教师必须先独立评分，再与 AI 结果比对**，否则锚定偏差导致结论无效 |
| 演示规模 | n = 30 可行，但文档须标注为「技术验证，非效度验证」 |

### 9.4 落地方式

```
eval/goldenset.jsonl    # 教师盲评结果（每行一个判定对）
eval/metrics.ts         # 计算上表全部指标
/eval 页面              # 混淆矩阵可视化：行=教师档，列=AI档
```

### 9.5 退出条件（提前承诺，避免越投越多）

| QWK | 结论 |
|---|---|
| ≥ 0.6 且低于教师间一致性上界 | 继续，方向是补足差异最大的那几类评分点 |
| 0.4 – 0.6 | 先做「评分点澄清」功能——这个区间通常说明标准本身模糊 |
| **< 0.4** | **停。路线不成立，继续加功能是浪费** |

> 补充：还应先测**教师之间的一致性上界**（两位教师独立评同一批报告算 QWK）。AI 的目标是达到教师间一致水平，超过既不可能也无意义。

## 第 10 章 两个 LearnBuddy Skill 的封装

### 10.1 为什么要封成 Skill

1. **开发期效率**：直接在 LearnBuddy 里调 Skill 跑单份样例，无需部署即可迭代 prompt
2. **交付演示**：答辩时是现成亮点
3. **评分挂钩**：赛事「AI 工具使用」占 25 分，按 LearnBuddy 历史对话记录评。用 Skill 开发的过程本身就是得分材料

### 10.2 两个 Skill

| 项 | Skill A | Skill B |
|---|---|---|
| 名称 | `autograder-evidence-extract` | `autograder-level-match` |
| 职责 | 材料 → 观察层 JSON（7 字段） | 证据 JSON + 细则 → 单点档位 |
| 输入 | 评分点 + 证据需求清单 + 章节索引 + 切片 | 单点证据 JSON + 该点 `levels` |
| 输出 | `EvidenceExtraction` | `LevelMatch` |
| 明确不做 | 不输出评价性词汇、不输出分数 | 不输出总分、不修改证据字段 |

两个 `SKILL.md` 已在本仓库 `skills/` 目录下。

### 10.3 唯一真相源原则

> **prompt 正文只维护一份，放在 `skills/*/SKILL.md`；Worker 侧构建时导入引用。**

禁止 Skill 与 Worker 各存一份 prompt——两处漂移是这类项目最常见的隐性故障：开发时调通了，上线后线上那份是旧的，表现不一致。

实现上，Workers 支持把 `.md` 作为文本导入：

```ts
import evidencePrompt from '../../skills/autograder-evidence-extract/SKILL.md';
```

### 10.4 输入输出契约

以 `SKILL.md` 中的「输入契约」「输出契约」两节为准，与附录 A 的 schema 保持字段级一致。

|---|---|---|
| `GET /health` | 存活检查 | 立即返回 200，不碰外部依赖 |
| `GET /ready` | 就绪检查 | 校验配置加载、D1 连通、R2 可写；任一失败返回 503 |

两个端点都必须**排除在限流之外**。

### 12.6 安全头与 CORS

```ts
// 安全头
'X-Content-Type-Options': 'nosniff',
'X-Frame-Options': 'DENY',
'Referrer-Policy': 'strict-origin-when-cross-origin',
'Strict-Transport-Security': 'max-age=31536000; includeSubDomains',
'Content-Security-Policy': "default-src 'self'; connect-src 'self'; img-src 'self' data:; frame-ancestors 'none'",

// CORS —— 显式来源，不用通配符
Access-Control-Allow-Origin: <命中的 ALLOWED_ORIGINS 项>
Vary: Origin
```

### 12.7 输入校验与限流

**所有输入在边界处校验，绝不信任客户端数据**：

| 输入 | 校验 |
|---|---|
| 上传文件 | 扩展名白名单（`.pdf` / `.docx`）、大小 ≤ `MAX_UPLOAD_BYTES`、MIME 嗅探 |
| 路由参数 | Zod 校验 ID 格式 |
| 请求体 | 每个 endpoint 一份 Zod schema |
| 评分点数量 | 上限 50 条（防止恶意构造超大 rubric） |

**限流**：按 IP + 路由维度，用 Durable Object 或 KV 计数器。`/api/grade/batch` 与上传端点必须限流。

### 12.8 数据库变更

**所有 D1 变更走迁移，只增不改**：

```bash
npx wrangler d1 migrations create autograder add_calibration_signal
npx wrangler d1 migrations apply autograder --local
npx wrangler d1 migrations apply autograder --remote
```

多步写入用一个 batch（D1 支持事务语义），例如"写入 FinalGrade 的同时写入 calibration_signals"，避免部分成功。

### 12.9 性能

- **避免 N+1**：草稿列表页要显示每份报告的评分点数时，用一次 `IN` 查询聚合，不要循环查
- **图片与大文本走 R2**，D1 只存结构化字段
- **报告解析结果缓存**在 R2，同一文件不重复解析

## 第 13 章 实施顺序与里程碑

按**风险从低到高**排序，而非按"用户最想要"排序。前四步都不产出最终判断，即使不准也不会造成教学事故，但已经能交付价值。

| 阶段 | 内容 | 产出 |
|---|---|---|
| M1 | 仓库骨架 + 配置校验 + 错误体系 + 健康检查 | 可部署的空壳，`/health` 与 `/ready` 通过 |
| M2 | 文档解析（`unpdf` / `mammoth` / 降级 `toMarkdown`）+ R2 存储 | 上传报告 → 得到结构化文本与章节索引 |
| M3 | 证据提取 + 引文回查 + 禁用词扫描 | 产出可信的观察层 JSON |
| M4 | 等级匹配 + 确定性算分 + 迁移 | 端到端跑通，得到分数与证据链 |
| M5 | 复核页（三层下钻）+ 改档与校准信号 | 教师可确认与校准 |
| M6 | Workflows 批量 + 进度轮询 | 30 份批量评阅 |
| M7 | 评测脚本与 `/eval` 页面 | QWK、一致率、混淆矩阵 |
| M8 | 生产加固补全（限流、安全头、日志面板）+ 演示快照降级 | 可对外演示 |

**M1–M4 是必须完成的底线。** 做到 M4，系统已经能产出"实验报告体检报告"：哪些代码跑不通、哪些结果对不上、全班在哪几个点上普遍失分——它不打分，因而完全避开高风险区，但已交付真实价值。

#### 决策 8 的说明：游客模式的具体形态

为压低演示门槛，不做账号体系：

- 首次访问时前端生成一个 `visitorId`（`crypto.randomUUID()`）存 `localStorage`
- 所有数据（rubric、报告、评分记录）按 `visitorId` 隔离
- 教师在校准时填一个"显示名"，同样存 `localStorage`，写入 `FinalGrade.confirmed_by`
- 页面提供「重置游客数据」按钮，用于演示前清场
- **限制须在 UI 上明示**：游客模式下数据不具备跨设备可携带性，也不构成真实身份认证

> 这条决策的适用范围是演示与验证阶段。真实投入使用需要替换为正式账号体系——但那不是本次范围。

#### 决策 9 的说明：为什么选 Vite + React 而不是 Next.js on Workers

| 维度 | Vite + React SPA | Next.js on Workers |
|---|---|---|
| 部署复杂度 | `wrangler deploy` 一条命令，前后端同仓同构建 | 需要 OpenNext 适配层，配置面大 |
| 与 Workers 契合度 | 构建产物直接作为 Static Assets | 需要处理 SSR runtime 兼容 |
| AI coding 友好度 | **改动面小、报错定位清晰** | 生成代码容易踩适配层坑 |
| 本项目是否需要 SSR | 不需要（纯客户端交互 + API） | —— |

结论清晰：**本项目没有 SSR 需求，上 Next.js 是纯增负担。**
