## 0. 三十秒理解这个项目

**AutoGrader 不是「AI 批作业」。**

它是：**把教师脑中的评分标准显性化，并把其中可机械化的部分从人身上挪走。**

这个定义不是修辞，它决定了整个架构。评分工作可以拆成两类：

| | 执行问题 | 判断问题 |
|---|---|---|
| 特征 | 有确定答案，可被核验 | 没有确定答案，需要有人承担后果 |
| 例子 | 读取解析文档、运行代码核对、定位原文证据、聚合统计、生成文字草稿 | 制定评分标准、定性判断创新性、雷同的最终定性、及格线判定、最终签字 |
| 归属 | **可以完全交给机器** | **必须留给人** |

**整个系统就是围绕这条线设计的。** 凡越过这条线的功能，一律不做——不是因为做不到，是因为做错了性质会变：产品从「效率工具」变成「责任主体」，而责任没法外包给模型。

赛题：深大计软 & 腾讯云「粤港澳大湾区 AI Coding 创新大赛」· 方向一「AI + 教学管理助手」· 官方赛题原文即包含 AutoGrader。

## 3. 详细设计

### 3.1 主链路（五段式）

```
①  评分细则 + 少量手改样本
        ↓
②  结构化证据提取（观察层，7 字段，零定性）
        ↓
③  带证据引用的自然语言评价
        ↓
④  等级匹配（L1–L4）
        ↓
⑤  程序确定性计算分数
        ↓
⑥  教师确认与校准
```

| 段 | 输入 | 输出 | 执行者 | 状态 |
|---|---|---|---|---|
| ① | 教师手写细则 | `Rubric` | 人 + 程序校验 | ✅ 已实现 |
| ② | `Rubric` + 材料文本 | `EvidenceExtraction` | 模型 + 程序后处理 | ✅ 已实现 |
| ③ | `EvidenceExtraction` | 带引用的自然语言 | 模型 | ⬜ 未实现（当前直接把结构化证据返回） |
| ④ | `EvidenceExtraction` + `levels` | `LevelMatch` | 模型 + 程序前置规则 | 🟡 prompt 与契约已就绪，编排未做 |
| ⑤ | `LevelMatch[]` + 权重 | `FinalGrade` | **纯程序** | ✅ 引擎已实现 |
| ⑥ | `FinalGrade` | 确认后的成绩 + 校准信号 | 人 | ⬜ 未实现 |

### 3.2 技术架构

| 层 | 选型 | 理由 |
|---|---|---|
| 运行时 | Cloudflare Workers | 公网可访问；`fetch()` 等待**不计入 CPU 时间**，所以长耗时 LLM 调用不撞限制 |
| 路由 | Hono | 轻量、无 Node 依赖 |
| 模型 | DeepSeek `deepseek-flash` | 中文与代码混合输入表现好；JSON Output 模式；约 ¥0.1/份 |
| 校验 | Zod v4 | 契约先行，输入输出双向校验 |
| 存储 | R2 + D1 | Workers 无持久文件系统 |
| 前端 | Vite + React SPA（计划） | 构建产物作为 Workers Static Assets；无 SSR 需求 |

**分层职责**（改动时请守住）：

| 层 | 做什么 | 明确不做 |
|---|---|---|
| `routes/` | 解析请求、校验入参、调服务、格式化响应 | **不写业务逻辑** |
| `services/` | 业务规则与编排 | **不依赖请求/响应对象**，可独立单测 |
| `repo/` | 数据访问 | 不含业务判断；避免 N+1 |
| `llm/` | 模型调用、JSON 守卫、重试 | 不含业务规则 |

`scoringService` 是纯函数：输入 `LevelMatch[]` + 权重，输出分数。它必须保持 100% 单测覆盖——**分数是这系统里唯一不能出错的部分**。

### 3.3 数据契约

四份契约，定义在 `src/schema/index.ts`，字段级说明见 `docs/附录-数据契约与Prompt.md`。

| 契约 | 作用 |
|---|---|
| `Rubric` | 评分细则。`criteria` 与 `scoring` 整份存 JSON |
| `EvidenceExtraction` | **观察层**。7 个字段，零定性 |
| `LevelMatch` | 单点评级 |
| `FinalGrade` | 最终评分记录 |

**观察层的 7 个字段**（这是全系统的核心契约）：

| # | 字段 | 对应问题 | 由谁产出 |
|---|---|---|---|
| 1 | `1_searched_materials` | 搜索过哪些材料 | 模型 |
| 2 | `2_found_quotes` | 找到了哪些原文 | 模型 |
| 3 | `3_locations_index` | 原文位置 | 模型给锚点，**字符偏移由程序回填** |
| 4 | `4_not_found` | 没找到什么 | 模型 |
| 5 | `5_surface_conflicts` | 是否出现表面冲突 | 模型 |
| 6 | `6_sufficiency` | 材料是否足以判断 | **程序** |
| 7 | `7_parse_failures` | 解析是否失败 | **程序** |

**被刻意排除的字段**：`score`、`grade`、`level`、`quality`、`comment`、`is_good`。

**`5_surface_conflicts.nature` 是枚举闭集**，只允许 `factual_mismatch` / `numeric_mismatch` / `internal_inconsistency`。**禁止**出现 `plagiarism`、`cheating`、`dishonest`、`suspicious`——相似度高不等于抄袭，定性需要解释规则，而规则是人定的。

### 3.4 四道防线（读这一节再改核心代码）

#### 防线一：观察层去定性化

**判据是一句可操作的话**：

> **「没找到」是事实，「不合格」是判断。**

| ✅ 观察 | ❌ 判断 |
|---|---|
| 在 §2.1 找到原文：「……」 | 原理说明写得完整 |
| 在 p.3-4 内检索 waitpid，未找到匹配 | 缺少对 waitpid 的处理 |
| 正文 p.2 称使用多进程；代码 p.6 仅 1 次 fork，无 wait 调用 | 正文与代码矛盾，涉嫌造假 |
| 该评分点要求的 r2 未获得匹配 | 该评分点不合格 |

实现是三层，缺一不可：

| 层 | 机制 | 失败处理 |
|---|---|---|
| L1 Prompt | 禁用词表 + 句式模板 + 自检指令 | 无效则进入 L2 |
| L2 Schema | Zod 枚举约束，闭集 | 校验失败即拒收 |
| **L3 后置扫描** | 程序扫描输出中的禁用词 | **命中即拒收并重生成，最多 2 次** |

只有 L3 把「防定性」从口头承诺变成机器约束。

**⚠️ 扫描范围有讲究**：只扫**模型自己撰写**的字段（`query` / `expected` / `claim` / `observed`），**绝不能扫 `2_found_quotes[].text`**。

因为那是**学生报告里的逐字摘录**——学生完全可能自己写「本次实验顺利完成，效果很好」。扫它就会把学生的用词误判成模型的定性，导致拒收一份完全正常的观察层。

因此两道防线的分工是：

| 关注点 | 由谁负责 |
|---|---|
| 摘录是否可信 | `quoteVerify`（不是逐字原文就丢弃） |
| 模型是否在下判断 | `judgementScan`（只扫模型撰写字段） |

**调用顺序：先 `verifyQuotes`，再 `scanJudgement`。**

**误报与漏报的取舍**：`错误`、`问题` 已从硬禁用词表移除。它们在技术语境有大量合法用法（「错误处理分支」「错误码」「问题分析与改进」甚至是章节标题）。**误报的代价远高于漏报**——误报会拒收整个观察层并触发重生成，既花钱又可能反复失败。改为只收复合评价形式：`有问题`、`存在问题`、`逻辑错误`、`明显错误`。

#### 防线二：引文回查

**每条摘录必须能在解析文本中被真实找到。**

| 匹配结果 | 处理 |
|---|---|
| 精确命中（归一化后） | `verified = 'exact'`，回填真实偏移 |
| k-gram 投票 + Dice ≥ 阈值（默认 0.9） | `verified = 'fuzzy'`，回填偏移 |
| 都不通过 | **丢弃该条**，记录 `QUOTE_NOT_VERIFIABLE` |

**位置一律以程序计算结果为准，覆盖模型给的 `char_start` / `char_end`。**

两点实现注意：

- **用 k-gram 投票定位，不要用前缀锚点。** 早期版本拿摘录前 16 字符当锚点，错字只要落在锚点区间内，锚点串在原文里就不存在，函数直接返回 `null`——等于模糊匹配从未生效。k-gram 投票只依赖片段命中率，跨过错字的片段失效，其余照常投票。
- **用 Dice 而不是编辑距离。** Workers Free 只有 10ms CPU，O(n·m) 会炸。Dice 是 O(n)。

#### 防线三：等级匹配的程序裁量权

**模型提建议，程序下判决。** 这是 `levelMatchService.reconcileLevelMatch` 的职责，也是一条容易被"优化"掉的防线——它拦的正是模型越权。

四项程序裁定，模型声称"不需要"一律无效：

| 裁定 | 规则 | 不留痕的后果 |
|---|---|---|
| **封顶** | required 证据未满足时，档位强制压到 `cap_level_when_required_missing` | 模型给 L4，教师看到满分，而学生根本没实现那个必需功能 |
| **引用核对** | `evidence_refs` / `missing_refs` 必须命中真实存在的 `quote_id` / `expectation_id`，否则丢弃 | 模型可以引用不存在的证据来"支撑"任意档位 |
| **依据充分性** | 两个引用列表都为空 → `needs_human` | 无依据的档位会被当作有效判定进入算分 |
| **档位合法性** | `matched_level` 必须在细则 `levels` 里定义过，否则 `needs_human` | 档位无法换算系数，算分时静默变成 0 分 |

**`needs_human` 取并集，不取交集。** 程序规则判定需要人工的，模型说不需要也无效；反之亦然。任一方提出即成立——让错误漏出去的成本远高于多送一次人工。

**每一次程序干预都必须留痕（`adjustments`）。** 不写进记录，教师就只看到一个突然变低的档位，会以为系统出错了。更关键的是：AI 本来想给 L4、被程序压到 L2 这件事，本身就是教师复核时最需要的情报。

#### 防线四：确定性算分

```
raw_score_i    = weight_i × score_ratio(level_i)
computed_total = 100 × Σ raw_score_i / Σ weight_i     仅统计 needs_human = false 的评分点
final_total    = round_half_up(computed_total, 1) + Σ override_delta
```

**模型不参与出分。** 理由：

| 问题 | 模型出总分 | 程序算总分 |
|---|---|---|
| 可复现 | ✗ 同输入可能不同输出 | ✓ |
| 可追溯 | ✗ 说不出 76.5 从哪来 | ✓ 每一分可定位到评分点与档位 |
| 可校准 | ✗ 改规则要重训 | ✓ 改权重即可 |
| 可申诉 | ✗ 无法解释 | ✓ 可出示证据链 |

**三条硬规则**：

1. `needs_human` 的评分点**既不进求和，也不进分母**
2. 分母为 0 时返回 0，不除零
3. **程序永远不输出「及格 / 不及格」**——总分落在及格线 ±2 分内强制挂起等人工签字

### 3.5 数据模型

`migrations/0001_init.sql`，8 张表。**只增不改**，已应用的迁移文件不得修改。

| 表 | 存什么 | 备注 |
|---|---|---|
| `rubric` | 评分细则 | `criteria_json` / `scoring_json` 整份存。细则是「文档」，按整份版本化 |
| `submission` | 学生报告 | 只存 R2 的 key，大文本不进 D1 |
| `evidence` | 观察层 | 含 `quote_kept` / `quote_dropped`，便于直接看幻觉率 |
| `level_match` | 单点评级 | |
| `grade` | 最终评分记录 | 完整快照。**一经确认即为证据，不随细则改动而变** |
| `calibration_signal` | 校准信号 | 教师每次改档记一条，**只建议不自动改规则** |
| `grade_task` / `grade_task_item` | 批量任务 | 供 Workflows 用 |

所有业务表都有 `owner_id`——游客模式下是前端生成的 `visitorId`。**它不是身份认证，只是数据隔离**，UI 上必须明示这一点。

### 3.6 中间件顺序

```
requestContext   → 生成 requestId、装配 logger（**不做配置校验**）
securityHeaders  → 安全响应头
cors             → 显式来源白名单
requireConfig    → 业务路由的配置校验（仅 /api/*）
visitor          → 解析 ownerId
rateLimit        → 限流
```

**两个刻意的设计**：

1. **配置校验不放在 `requestContext`**。`/health` 必须在配置损坏时依然可用——否则无法区分「服务活着但配置错了」和「服务挂了」。
2. **健康检查排除在限流之外**。否则探针会被自己的限流挡住。

### 3.7 接口清单

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/health` | 存活检查，不碰外部依赖 |
| GET | `/ready` | 就绪检查：config / D1 / R2 |
| GET | `/api/version` | 版本与模型名 |
| GET | `/api/rubrics` | 细则列表（不含 criteria） |
| POST | `/api/rubrics` | 新建，版本号按同标题自增 |
| GET | `/api/rubrics/:rubricId` | 细则详情 |
| PUT | `/api/rubrics/:rubricId` | 原地修订，**版本号不变** |
| DELETE | `/api/rubrics/:rubricId` | 删除 |
| POST | `/api/evidence/extract` | 从纯文本抽取观察层 |
| POST | `/api/grade` | **完整链路**：抽取 + 匹配 + 算分（每评分点 2 次模型调用，限流 5/min） |
| POST | `/api/grade/recompute` | **只算分**：输入 matches + overrides，纯函数，毫秒级。教师改档用这个 |

**为什么 `/api/grade` 与 `/api/grade/recompute` 要拆开**：教师复核时改一次档位，若走完整链路就要重跑全部模型调用、等几十秒；而改档只影响算分，不该牵动模型。拆开之后复核页的交互是即时的——这是「教师确认与校准」这个环节能不能被真正用起来的前提。

所有 `/api/*` 需要 `X-Visitor-Id` 头（游客模式）。

**错误响应统一结构**：

```json
{ "error": { "code": "PARSE_FAILED", "message": "…" }, "requestId": "req_…" }
```

`internal` 只进日志，绝不进响应。

### 3.8 关键设计决策速查

改代码前扫一眼，避免"优化"掉有意为之的东西。

| 决策 | 理由 |
|---|---|
| 细则的 `criteria` 整份存 JSON | 细则是文档不是记录，拆行后版本快照无法还原 |
| `updateRubric` 不升版本号 | 原地修订。要留档应新增 fork 接口，否则历史评分记录与版本对不上 |
| 至少要有一条 `execution` 类型评分点 | 全是判断型的话系统无事可做，这类「建得出来但没用」的输入应在边界挡掉 |
| 章节索引用纯函数而非调模型 | 确定性、零 token、位置来自解析器比模型"目测"更准 |
| `6_sufficiency` 由程序判定 | 让模型自由判断会让它退化成「这份报告写得好不好」 |
| 抽取接口刻意串行 | 瓶颈是模型延迟；并发受 Workers 出站连接（6）约束 |
| 空 content 视为可重试 | DeepSeek JSON Output 的已知偶发行为，不是格式错误 |
| 正则写错时退化为字面量匹配 | 不让一个坏规则把整份报告判成缺失 |
| 切片只用叶子章节 | 父章节范围包含子章节，两者都选会让内容重复送模型 |
| 只扫模型撰写字段 | 见 §3.4 防线一 |
| 模型不输出 `criterion_id` | 由程序填入。让模型自报"评的是哪个点"，一旦串号错误会静默传播 |
| 封顶由程序强制施加，不听模型 | 见 §3.4 防线三。这不是不信任，是这类判定不该由概率模型承担 |
| `needs_human` 取并集而非交集 | 任一方提出即成立，错误漏出去的成本远高于多送一次人工 |
| 程序每次干预都留痕（`adjustments`） | AI 想给 L4 被压到 L2，这本身就是教师最需要的情报 |
| 单评分点失败不中断整批 | 一条评不出来不该导致整份报告评不了分，否则教师连部分结果都拿不到 |
| `judgment` 类型显式记录而非静默跳过 | 否则教师会以为系统漏评了 |
| 算分拆出独立接口 | 教师改档要即时反馈，不能等几十秒重跑模型 |

## 5. 已知的坑

**这些坑都实际踩过，写下来是为了不重复踩。**

### 环境类

| 坑 | 表现 | 解法 |
|---|---|---|
| **npm 官方源不通** | `npm install` 静默卡死，无输出无报错 | 项目根 `.npmrc` 指定 `registry=https://registry.npmmirror.com` |
| **`wrangler dev` 默认走远程绑定** | 去建 cloudflared 隧道 → 被代理拦截 → dev server 退出 | `package.json` 的 dev 脚本已改为 `wrangler dev --local`。官方文档：`--local` 会禁用全部远程绑定 |
| **`wrangler d1 create` 会污染配置** | 自动往 `wrangler.jsonc` **追加**一条带 `remote: true` 的绑定，且与手写的那条并存 | 每次执行 `wrangler * create` 后回读 `wrangler.jsonc` 确认 |
| **端口被占时 wrangler 静默换端口** | 打 8787 得到完全对不上的响应体 | 用 `/health` 打指纹；`netstat -ano \| findstr :8787` |
| **代理劫持 localhost** | `wrangler login` 的 OAuth 回调超时 | 改用 `CLOUDFLARE_API_TOKEN`，完全绕开本地回调 |
| **`env.AI` 在 `--local` 下不可用** | 文档解析会失败 | 见「待解决问题」第 4 条 |

### 代码类

| 坑 | 说明 |
|---|---|
| **zod v4 的 `.default()` 要求完整输出类型** | `.default({})` 会报「No overload matches」。必须传完整对象（见 `schema/index.ts` 的 `DEFAULT_SCORING`） |
| **带 `g` 标志的正则复用要重置 `lastIndex`** | 否则跨字段扫描会漏检，第二个字段开始再也匹配不到 |
| **PowerShell 里 `curl` 是 `Invoke-WebRequest` 的别名** | 必须写 `curl.exe` |
| **`Get-Content` 相对路径依赖当前目录** | 手动执行时容易在错误目录下跑命令 |

## 6. 协作约定

### 提交

- 分支：`main` 直接开发，功能较大时开 `feat/xxx`
- 提交信息用中文，格式 `<type>: <描述>`，type 取 `feat` / `fix` / `docs` / `refactor` / `test` / `chore`
- **提交前必须**：`npm run typecheck` 无输出 + `npm test` 全绿

### 目录约定

- 新接口 → `src/routes/`，业务逻辑放 `src/services/`，SQL 放 `src/repo/`
- 新契约 → 先改 `src/schema/index.ts`，再同步 `docs/附录-数据契约与Prompt.md`
- 改 prompt → 必须升 `prompts.ts` 里的版本号，否则历史结果无法归因
- **数据变更走迁移，只增不改**

### 绝对不要提交

- `.dev.vars`（含真实密钥）
- 任何真实学生报告（`data/real/`、`fixtures/real/`、`uploads/` 已在 `.gitignore`）
- `.npmrc`（会让其他网络环境的人安装变慢）

### 改核心代码前的自检

1. 这个改动会不会让观察层混进判断？（防线一）
2. 会不会放行一条无法定位的引文？（防线二）
3. 会不会让模型影响到分数？（防线三）
4. 会不会让 `/health` 依赖上业务配置？

**四个问题答不上来就先别改。**
